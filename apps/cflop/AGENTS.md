# AGENTS.md

## 1. Overview
`apps/cflop` is the Vite + React app for learning and drilling 3x3 Rubik's Cube OLL and PLL last-layer algorithms. It has no backend dependency: algorithm data is bundled at build time, and per-case learning progress and the training pool are kept in the browser's `localStorage`.

## 2. Folder Structure
- `src/app`: router creation and `app-shell.tsx`, which wraps `ToolShell` from `@unimatrix/chrome/tool`. The frame, background and skip link come from the package; this app supplies only the source link, the jperm.net attribution and `homeHref`. No `accountControl` is passed, so the shell renders no title bar.
- `src/features/algorithms`: algorithm case data (`*.data.ts`, scraped from jperm.net/algs), `algorithm-sets.ts` (the `AlgorithmSet` registry), `types.ts`, `derive-diagram.ts` (maps a case to its last-layer diagram), `preview-mode.ts` (the preview-mode union plus which modes each set offers), `use-algorithm-set.ts`/`use-case-pool.ts`/`use-case-progress.ts`/`use-preview-mode.ts` (hooks over the `localStorage` stores below), and components including the OLL/PLL segmented toggle, the preview-mode toggle, `case-diagram-view.tsx` (picks the renderer for the active preview mode), `panel-action-bar.tsx` (the key-hint/button row both panels end in), `case-selection.ts` (pure pool arithmetic — per-group enabled/total counts, and the id -> enabled record a bulk action writes), case preview card, algorithm group section, and `case-selection-menu.tsx` (the drill-pool bulk-edit menu).
- `src/features/cube`: the cube-notation/diagram engine — `engine.ts` (move/notation application over a cube model), `model.ts` (facelet model), `notation.ts` (move-string parsing), `last-layer-diagram.ts` (derives both the flat last-layer diagram and the two-sided `CornerDiagram` from a case), `corner-projection.ts` (pure isometric screen geometry for the two-sided view), and `components/last-layer-diagram-view.tsx` / `components/corner-diagram-view.tsx` (render them). This is the shared computational core behind case previews and diagrams; it is not scraped data like `algorithms/*.data.ts`.
- `src/features/learn`: guided teaching flow — session hook (`use-learn-session.ts`), fixed group+weight case ordering (`learn-case-order.ts`), and the panel/cases-grid/set-view components. The cases grid reads (but does not write) case progress to badge learned cases; picking a card reports the case up to the set view, which opens the session on it.
- `src/features/trainer`: keyboard-driven drill flow — trainer hook (`useAlgorithmTrainer`), uniform next-case selection (`pick-next-case.ts`), case setup, and the panel/cases-grid/set-view components plus `drill-choose-cases-view.tsx`, which owns the pool for the whole picker.
- `src/lib/local-storage.ts`: the one place the `localStorage` key namespace is decided, plus the shared quota/private-browsing-safe read and write. The key families below build their suffixes and go through it.
- `src/lib/progress-storage.ts`: Zod-validated `localStorage` read/write for per-case learned status (`new` | `learning` | `known`); written only by the Learn session, but also read by Learn's and Drill's cases grids to badge/filter by learned status.
- `src/lib/pool-storage.ts`: Zod-validated `localStorage` read/write for the per-case training pool (manual enable/disable), used only by Drill's case-picker. `setCaseEnabled` writes one case; `setCasesEnabled` takes a whole id -> enabled record, so a bulk action is one read/write and a mixed change (Enable only learned) stays atomic.
- `src/lib/preview-mode-storage.ts`: Zod-validated `localStorage` read/write for the diagram preview mode. Keyed by view (`learn`/`drill`), not by case or algorithm set.
- `src/lib/algorithm-set-storage.ts`: Zod-validated `localStorage` read/write for the selected OLL/PLL set. One unscoped key, because Learn and Drill share the choice.
- `src/routes`: file-based route loaders and lazy route components; keep paired `*.ts(x)` and `*.lazy.tsx` files aligned. Routes are `/` (Learn-vs-Drill chooser), `/learn`, and `/drill`. `routeTree.gen.ts` is generated and should not become a hand-edited source of truth.
- `src/styles.css`: app-specific presentation layered on top of `@unimatrix/ui/styles.css`.
- `test`: Vitest. `local-storage.test.ts` asserts against literal key strings on purpose — a test that only round-trips through the writers passes just as happily with the `cube-trainer:` fallback deleted.
- `e2e`: Playwright smoke coverage for the running app.

## 3. Core Behaviors & Patterns
- **Algorithm data provenance**: `oll-algorithms.data.ts` and `pll-algorithms.data.ts` were generated from jperm.net's own trainer data files (`/lib/oll.js`, `/lib/pll.js`), not hand-transcribed. If the upstream algorithm sets change, regenerate rather than hand-editing individual entries.
- **Learn vs Drill, not Browse vs Trainer**: `/` is a mode chooser; the OLL/PLL toggle lives inside `/learn` and `/drill`, not as separate top-level routes. Learn walks unknown cases in a fixed group+weight teaching order (`orderedLearnCases`) and marks a case "known" directly when the user acts on it — learned status is the only per-case flag Learn has, there is no separate hide-from-learn flag. Drill drills whatever is manually enabled in the training pool, independent of learned status.
- **A learned case must stay readable, and pinning is how**: the teaching walk excludes known cases, so marking one learned is exactly what takes its algorithm off screen. Learn's case grid is the way back — a card opens that case in the session (`LearnPanel`'s `initialCaseId`) instead of toggling anything. A picked case that is *still in the walk* just moves the cursor there. A picked case that is **learned** has no position in the walk, so the session **pins** it: `canGoBack`/`canGoNext` are both false, so neither arrow renders as a control, and Space reads "Unlearn". Unmarking hands it back — the cursor is set from the re-ordered walk in the same call that writes the status, so navigation returns *with that case under the cursor* rather than dumping you at the start. Learned cards keep their badge and border but are **not** dimmed: dimming reads as "finished with" on the one screen whose job is looking an already-learned algorithm back up. Drill's grid still toggles the pool on click, so `CasePreviewCard` takes what the click means from the caller (`pressed` for Drill's toggle, neither `pressed` nor `dimmed` for Learn).
- **Two independent per-case stores**: `progress-storage.ts` (learned status: new/learning/known, written only by the Learn session, but also read by Learn's and Drill's cases grids to badge/filter by learned status) and `pool-storage.ts` (training pool: boolean enabled/disabled, read/written only by Drill's case-picker) are separate `localStorage` keys (`cflop:progress:<setId>` and `cflop:pool:<setId>`) and do not sync with each other. `preview-mode-storage.ts` (`cflop:preview-mode:<learn|drill>`) and `algorithm-set-storage.ts` (`cflop:algorithm-set`, one key with no suffix segment) are the other two families, and both are view preferences rather than per-case state.
- **Reads fall back to the `cube-trainer:` prefix**, in `local-storage.ts` and nowhere else. Real browsers hold learned-case status and training pools under that prefix, and nothing can tell which ones have written since. Deleting the fallback discards their data with no error and no visible symptom beyond "all my progress is gone", so it stays; the cost of keeping it is one extra `getItem` on a cache miss. Writes only ever target `cflop:`, and each carries the data forward through the read-merge every writer already does.
- **Preview modes are per view, clamped per set**: the panel diagram renders top-down, two-sided, or hidden. OLL offers top-down/hidden; PLL adds two-sided (an isometric U-F-R corner with the lower two layers greyed). Learn and Drill store the preference separately, since drilling usually wants it hidden and teaching does not. The **set** is the deliberate opposite: it is one shared key, so switching modes keeps whichever of OLL/PLL you were working on. Preference-per-view and set-shared are both intentional — do not "fix" either into matching the other. The stored value is deliberately *not* rewritten when OLL is selected, so `two-sided` survives a round trip; `resolvePreviewMode` clamps at render time and its result must also be what the toggle receives as `value`, or Radix renders the group with nothing selected. **The storage-miss default and the clamp fallback are separate values and must stay that way**: `INITIAL_PREVIEW_MODE` is `two-sided`, so a set that offers it opens on it, while `PREVIEW_MODE_FALLBACKS` gives OLL `top-down`. Collapsing them back into one shared default clamps OLL to a mode it does not offer, which is the empty-toggle failure above. The Choose-cases grids always render top-down regardless of the mode.
- **Drill's picker selects, it does not filter**: the menu in the Choose-cases title bar (`Drill pool  21/57`) edits the pool — Enable all / Disable all / Enable only learned over the whole set, and a checkbox per category showing `enabled/total`. It must edit the pool rather than card *visibility* — hiding a card chooses nothing about what you actually drill. The grid therefore always renders every case: bulk edits have to be visible in the cards behind the menu, and with nothing hidden there is no "no cases match" state left. Category rows show counts rather than a tri-state box because the checkbox indicator is a single tick, so partial and full would look identical. `DrillChooseCasesView` owns `useCasePool` for both the menu and the grid — two copies of the hook each hold their own `useState` snapshot, so the grid would render the pool as it was before a bulk action; it takes `key={setId}` because the store hooks read `localStorage` in a lazy initializer.
- **Reserved space is load-bearing, not padding**: the move-string wrappers hold two lines of `leading-7` on a coarse pointer, the alternates disclosure row holds its button's line box at every width, and an unavailable arrow holds its slot. Each is there because that element's height varies between cases, and without it the cube and the action row move as you walk the set. They read as dead styling and are not. The reservation is not total — some PLL algorithms wrap to three lines below ~390px, so those cases still shift.
- **Drill draws uniformly; `probabilityWeight` is Learn's**: `pickNextCase` picks the next flashcard from the enabled pool with equal probability, skipping an immediate repeat whenever more than one case is enabled — with equal weights that skip leaves the long-run distribution uniform, so it is not a bias. `probabilityWeight` (jperm's real-world OLL/PLL case frequency) has exactly one consumer, `orderedLearnCases`. It is live data, not a leftover.
- **Keyboard-driven, with the same actions as buttons on a coarse pointer**: Drill uses Space to advance to the next drill case; Learn uses ArrowLeft/ArrowRight to move back/forward through the teaching order and Space to mark the current case learned (or unmark it, when the case is pinned — see above). The keys are always live. What changes with the pointer is only how the action is advertised: `PanelActionBar` renders both a key hint and a button for every action and swaps them on `@media (pointer: coarse)` alone, so a touch device gets tappable controls and a laptop gets hints. `canGoBack`/`canGoNext` gate the control, not the space it sits in: an unavailable arrow is `visibility: hidden`, out of the accessibility tree, the tab order and the hit area, while its slot stays — never a disabled control. Learn's window keydown listener returns early for an event inside `[data-panel-action]`, or Space on a focused Back button would run the learned toggle and `preventDefault()` would swallow Back's own activation.

## 4. Conventions
- **Route files**: paired non-lazy/`*.lazy.tsx`, as in `apps/web`.
- **Imports**: Group external imports first, then `@/` aliases, then relative imports. Prefer `@unimatrix/ui/public` over the full `@unimatrix/ui` surface.
- **Naming**: Components use `PascalCase`; helpers and data modules use `camelCase` exports from kebab-case files.
